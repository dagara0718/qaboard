# QANOW 질의응답 게시판 Constitution

## Core Principles

### I. 명확한 권한 분리

**Rules:**

- 회원(일반 사용자)과 관리자의 권한을 응용 계층과 데이터 계층에서 모두 명확히 분리한다.
- 권한 그룹: 게스트(비로그인), 회원(로그인 사용자), 관리자(콘텐츠/시스템 관리)
- 각 권한별 수행 가능한 작업(질문 작성/편집, 답변 작성/편집, 삭제, 회원 관리 등)을 명세에 명시한다.
- 기본값은 최소 권한 원칙(Principle of Least Privilege)을 따른다.

**Rationale:**
보안과 데이터 무결성을 보장하기 위해 사용자별로 수행할 수 있는 작업을 명확히 제한해야 한다. 권한 체계가 애매하면 무단 접근, 데이터 손상, 규정 위반으로 이어진다.

**Review Criteria:**

- PR에서 새 엔드포인트/쿼리 추가 시 권한 검증 로직이 포함되었는가?
- 관리 페이지 접근 제어 테스트 케이스가 있는가?
- 권한 명세 문서와 코드가 일치하는가?

### II. 데이터 계층 권한 강제

**Rules:**

- UI 제약만으로는 보안을 보장하지 않는다. 모든 데이터 변경(CREATE, UPDATE, DELETE)은 데이터베이스 계층에서 권한을 최종 검증해야 한다.
- API 엔드포인트는 요청 사용자의 권한을 항상 서버 세션/토큰으로 확인한다. 클라이언트 제공 권한 정보는 신뢰하지 않는다.
- 데이터 쿼리는 권한 필터(WHERE 절)를 자동으로 적용한다. 예: 회원이 작성한 질문만 조회 가능.

**Rationale:**
클라이언트는 공격자가 수정할 수 있다. 서버 데이터베이스 계층에서 권한을 재확인하지 않으면 무권한 접근과 데이터 변조가 가능하다.

**Review Criteria:**

- UPDATE/DELETE 쿼리가 사용자 ID 필터를 포함하는가? (예: `WHERE id = ? AND author_id = ?`)
- API 핸들러가 서버 세션에서 사용자 권한을 검증하는가?
- 데이터베이스 마이그레이션에 CHECK 제약조건이나 행-수준 보안(RLS) 정책이 포함되는가?

### III. 사용자 입력 검증

**Rules:**

- 모든 사용자 입력(폼, API, URL 매개변수)은 서버에서 검증해야 한다.
- 검증 항목: 데이터 타입, 길이 제한, 형식(이메일, URL 등), 범위, null 여부 등.
- 클라이언트 검증은 UX를 위한 것이며, 서버 검증이 보안을 담당한다.
- 검증 실패 시 명확한 오류 메시지를 클라이언트에 반환한다(민감 정보 노출 제외).

**Rationale:**
유효하지 않은 입력은 주입 공격(SQL, XSS), 버퍼 오버플로우, 논리 오류로 이어진다. 서버 검증 없이 신뢰할 수 없다.

**Review Criteria:**

- API 엔드포인트가 입력 검증 함수를 호출하는가?
- 검증 로직을 단위 테스트로 검증했는가? (경계값, null, 특수 문자 등)
- 오류 응답이 스택 트레이스나 데이터베이스 스키마를 노출하지는 않는가?

### IV. 명세 준수

**Rules:**

- 명세 문서에 정의되지 않은 기능은 구현하지 않는다.
- 기능 추가나 변경이 필요하면 먼저 명세를 수정하고, 사용자(또는 이해관계자) 승인을 받은 후 구현한다.
- 임시 방편, 미래를 위한 "확장성" 고려, 추측에 기반한 기능 추가는 금지한다.
- 명세와 구현 사이의 불일치가 발견되면 명세를 우선으로 간주한다.

**Rationale:**
범위 확대(scope creep)를 방지하고, 프로젝트를 단순하고 유지보수하기 쉽게 유지한다. 불명확한 기능은 버그, 성능 문제, 보안 취약점의 원인이 된다.

**Review Criteria:**

- 새 기능이 명세 문서에 명시되었는가?
- PR 설명에 "왜 이 기능을 추가했는가"가 명확하게 기술되었는가?
- 명세에 없는 엣지 케이스나 가정을 코드에 추가하지 않았는가?

### V. 세 핵심 화면의 정보 구조 및 디자인 일관성

**Rules:**

- 프로젝트의 핵심 화면(목록, 상세, 작성/편집)의 정보 구조, 레이아웃, 색상, 타이포그래피를 일관되게 유지한다.
- 동일한 데이터(예: 작성자 정보)는 모든 화면에서 같은 시각적 스타일로 표시한다.
- 네비게이션, 버튼 배치, 입력 필드 배열이 화면 간에 일관성을 가진다.
- 디자인 변경 시 모든 관련 화면을 검토하여 일관성을 유지한다.

**Rationale:**
일관된 디자인은 사용자의 인지 부하를 줄이고 학습 곡선을 단축한다. 화면마다 다른 패턴은 사용자를 혼란스럽게 하고 실수를 유발한다.

**Review Criteria:**

- 새 컴포넌트나 스타일 변경 PR에 세 화면의 스크린샷이 포함되었는가?
- 색상, 폰트 크기, 간격이 디자인 시스템(또는 일관된 패턴)을 따르는가?
- 접근성 테스트 결과(색상 대비, 포커스 순서 등)가 일관되는가?

### VI. 메인 페이지의 시각 효과 제약

**Rules:**

- 메인 페이지의 애니메이션, 그림자, 그래디언트, 배경 이미지 등 시각 효과는 성능과 가독성을 고려해야 한다.
- 효과 적용 전에 성능 측정(First Contentful Paint, Cumulative Layout Shift 등)을 수행한다.
- 효과로 인한 콘텐츠 가독성 저하(예: 텍스트 대비율 감소)는 허용되지 않는다.
- 과도한 효과(연속 애니메이션, 과다한 필터)는 배제한다.

**Rationale:**
사용자는 정보를 빠르고 쉽게 얻기를 원한다. 시각 효과가 로딩 속도를 저하시키거나 콘텐츠를 방해하면 사용자 경험을 해친다.

**Review Criteria:**

- 메인 페이지 로딩 성능 측정(Lighthouse 등)에서 성능 점수가 80점 이상인가?
- 모든 텍스트의 색상 대비율이 WCAG AA 기준을 충족하는가?
- 크로스 브라우저/기기에서 버벅거림이 없는가?

### VII. 애니메이션 접근성

**Rules:**

- 모든 애니메이션은 `prefers-reduced-motion` 미디어 쿼리를 존중해야 한다.
- 전정기관 장애(vestibular disorder)나 전정 민감도가 높은 사용자를 배려한다.
- 시스템 설정에서 "동작 줄이기"를 활성화한 사용자는 즉각적인 상태 변화(애니메이션 제외)만 볼 수 있어야 한다.
- 애니메이션은 기능적 필수 요소가 아니어야 한다(정보 전달은 다른 방식으로도 가능해야 함).

**Rationale:**
전정 장애나 감각 민감도가 높은 사용자는 부드러운 움직임으로 인해 어지러움, 메스꺼움, 두통을 경험할 수 있다. 기술적으로 접근성을 보장하는 것이 법적 요구사항이기도 하다.

**Review Criteria:**

- CSS에서 `@media (prefers-reduced-motion: reduce)` 블록이 모든 애니메이션을 제거하는가?
- JavaScript 애니메이션이 `window.matchMedia('(prefers-reduced-motion: reduce)').matches` 검사를 포함하는가?
- 시스템 접근성 설정 활성화 후 테스트했는가?

### VIII. 키보드 접근성

**Rules:**

- 모든 주요 사용자 작업(질문 검색, 답변 등록, 수정, 삭제, 투표 등)을 키보드만으로 수행할 수 있어야 한다.
- 마우스 호버나 터치 제스처에만 의존하는 UI 패턴은 금지한다.
- 포커스 표시(outline, border 등)는 명확하고 시각적으로 구별되어야 한다. 기본 브라우저 포커스 스타일을 제거할 때는 반드시 대체 스타일을 제공해야 한다.
- Tab 키로 모든 상호작용 요소를 순환할 수 있어야 한다. 포커스 순서가 논리적이어야 한다.

**Rationale:**
키보드 사용자(신체 장애, 선택 장애, 장비 선호도)를 배제하면 안 된다. 또한 마우스가 없는 환경(터미널, 접근성 도구)에서도 작동해야 한다.

**Review Criteria:**

- 마우스를 사용하지 않고 Tab, Enter, Escape 키만으로 주요 워크플로우를 완료할 수 있는가?
- 포커스 표시가 배경과 충분한 대비를 가지는가? (최소 3:1)
- 포커스 순서가 시각적 순서와 일치하는가?
- 키보드 사용을 테스트한 기록이 있는가?

### IX. 상태 표현의 이중성

**Rules:**

- 상태(예: 해결됨, 미해결, 차단됨, 진행 중)는 색상 만으로 구분하지 않는다.
- 모든 상태는 텍스트 라벨, 아이콘, 또는 시각적 신호(패턴, 선 굵기 등)를 함께 사용하여 표현한다.
- 색맹 사용자(약 8% 남성, 0.5% 여성)도 상태를 명확히 식별할 수 있어야 한다.
- 상태 변화는 시각적 신호와 함께 필요시 알림(배지, 토스트)으로도 표현한다.

**Rationale:**
색각 이상(색맹, 색약) 사용자는 특정 색을 구분하지 못한다. 색상만으로 정보를 전달하면 이들은 상태를 파악할 수 없다.

**Review Criteria:**

- 모든 색상 상태 표현에 텍스트 라벨이 있는가?
- 그레이스케일 또는 색맹 필터를 적용한 후에도 상태를 식별할 수 있는가?
- 접근성 감사 도구(WebAIM, axe 등)가 "색상만으로 정보 전달" 문제를 탐지하지 않는가?

### X. 데스크톱 및 모바일 시나리오 완성도

**Rules:**

- 핵심 사용자 시나리오(질문 작성, 답변 제공, 투표 등)는 데스크톱과 모바일 환경에서 모두 완료 가능해야 한다.
- 반응형 디자인(Responsive Design)을 기본으로 한다. 모바일 환경에서 기능이 빠지거나 동작하지 않으면 안 된다.
- 터치 대상(버튼, 링크)은 최소 44×44px 크기를 권장한다(WCAG 기준).
- 모바일 제약(느린 네트워크, 작은 화면, 배터리 소모)을 고려하여 기능을 단순화한다.

**Rationale:**
모바일 트래픽은 전체의 상당 부분을 차지한다. 모바일에서 핵심 기능이 작동하지 않으면 사용자 이탈이 발생한다. 또한 법적 요구사항(WCAG)이기도 하다.

**Review Criteria:**

- 크롬 DevTools 모바일 에뮬레이션에서 시나리오를 완료했는가?
- 모바일 환경에서 버튼과 링크가 쉽게 탭 가능한가?
- 네트워크 시뮬레이션(Slow 3G) 환경에서 로딩 시간이 허용 범위 내인가?
- iOS와 Android 기기에서 테스트했는가?

### XI. MVP 단순성 우선

**Rules:**

- 프로젝트는 최소 실행 가능 제품(MVP)의 원칙을 따른다.
- 미래의 필요성을 추측하여 기능을 추가하지 않는다(YAGNI: You Aren't Gonna Need It).
- 기존 기능을 일으켜 기능을 추가할 수 없다면, 복잡도 증가를 재검토한다.
- 코드 라인 수, 파일 개수, 의존성이 최소화되어야 한다.
- 기존 라이브러리, 프레임워크, 표준 패턴을 우선 사용한다.

**Rationale:**
단순한 코드는 이해하기 쉽고, 버그가 적고, 유지보수 비용이 낮다. 과도한 추상화나 선제적 설계는 기술 부채를 증가시킨다.

**Review Criteria:**

- 새 기능 PR의 코드 라인 수가 500줄을 초과하지 않는가?
- 새 의존성 추가가 정당화되는가? (기존 도구로 불가능한가?)
- 코드가 이해하기 쉬운 이름과 간단한 논리를 사용하는가?
- 테스트 커버리지가 80% 이상인가?

### XII. Task 요구사항 및 설계 추적성

**Rules:**

- 모든 구현 Task는 명세, 디자인 문서, 사용자 스토리 또는 이슈로 링크되어야 한다.
- Task 설명에는 "왜 이를 구현하는가"(비즈니스 가치, 사용자 요구)가 명시되어야 한다.
- PR 설명에는 관련된 Task 번호, 명세 섹션, 디자인 권장사항이 참조되어야 한다.
- 코드 리뷰 시 "명세에서 정의한 동작과 일치하는가?"를 확인한다.

**Rationale:**
설계와 구현의 관계를 명확히 하면, 미래 유지보수자가 왜 이 코드가 존재하는지 이해할 수 있다. 또한 실수나 편향을 줄인다.

**Review Criteria:**

- 모든 PR에 Task/이슈/명세 참조가 있는가?
- PR 설명이 "무엇을" 뿐 아니라 "왜"를 설명하는가?
- Task 제목이 구체적인가? ("기능 개선" 같은 모호한 제목은 없는가?)
- 코드 주석이 과도하지 않으면서도 비명확한 로직을 설명하는가?

### XIII. 테스트 및 빌드 검증

**Rules:**

- 모든 구현 작업의 완료 기준: 테스트와 빌드가 성공적으로 통과해야 한다.
- 테스트 실패, 빌드 오류, 타입 에러가 있으면 Task를 완료 상태로 표시할 수 없다.
- CI 파이프라인(예: GitHub Actions)이 자동으로 테스트와 빌드를 검증해야 한다.
- PR은 CI 검사를 통과해야만 머지할 수 있다(강제 규칙).

**Rationale:**
테스트와 빌드 성공은 코드 품질과 안정성의 최소 기준이다. 이를 생략하면 숨겨진 버그, 성능 저하, 보안 취약점이 프로덕션에 도달한다.

**Review Criteria:**

- PR의 CI 체크(테스트, 빌드, 린트)가 모두 통과했는가?
- 새 기능에 대한 단위 테스트 또는 통합 테스트가 있는가?
- 테스트 커버리지가 감소하지 않았는가?
- 로컬에서 `npm test` 및 `npm run build`가 성공하는가?

## Security & Data Integrity

모든 권한, 입력, 데이터 검증은 클라이언트가 아니라 서버/데이터베이스 계층에서 강제된다. 클라이언트는 공격자에 의해 수정될 수 있으므로 서버는 항상 검증을 수행해야 한다.

- SQL 주입, XSS, CSRF 공격을 방어하기 위해 안전한 라이브러리와 패턴을 사용한다.
- 민감 정보(비밀번호, 이메일)는 암호화하여 저장하고, 전송 중에는 HTTPS를 사용한다.
- 로깅은 감사 추적을 위해 중요하며, 모든 데이터 변경(작성, 수정, 삭제)을 기록한다.

## Development Workflow & Quality Gates

1. **작업 시작**: Task 생성 → 명세 검토 → 디자인 확인
2. **구현**: 명세와 디자인을 따름 → 임시 방편 금지
3. **테스트**: 단위 테스트(80% 커버리지) → 통합 테스트 → 접근성 테스트
4. **코드 리뷰**: 명세 준수 확인 → 보안 검토 → 성능 검토 → 접근성 검증
5. **배포**: CI 통과 → 병합 → 모니터링

**차단 기준:**

- 테스트 실패
- 빌드 오류
- 접근성 위반(WCAG AA 미만)
- 명세와 불일치
- 보안 취약점

## Governance

이 Constitution은 QANOW 프로젝트의 모든 개발 활동을 규정한다. Constitution은 다른 모든 관례보다 우선한다.

**개정 절차:**

1. 개정 제안: 이슈 또는 PR로 제안
2. 토론 및 합의: 팀 검토
3. 승인: 프로젝트 리더 승인
4. 문서 업데이트: Constitution 버전 증가
5. 이행: 새 규칙은 다음 스프린트부터 적용

**버전 정책:**

- MAJOR: 기존 원칙 제거 또는 근본적 변경
- MINOR: 새 원칙 추가 또는 기존 원칙 확장
- PATCH: 명확화, 오류 수정, 문구 개선

**준수 검증:**

- 모든 PR 리뷰에서 Constitution 준수 확인
- 정기 감사(분기별)를 통해 준수 상황 평가
- 위반 사항은 팀 내 공유 및 개선 논의
